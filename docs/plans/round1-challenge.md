# Devin Workspaces — Round 1 plan review

## Verdict: APPROVE WITH CHANGES

The core architecture is directionally right: embed Devin’s real Cloud UI rather than recreate a session manager on APIs the brief says lack folders and full worklog data; use Electron’s hosted Chromium views for the required GitHub pane; keep the native shell small. The plan is overbuilt around peripheral browser controls and under-decided around Local session UX, tab ownership, and authentication. Electron is a reasonable default, not yet a proven winner: Google OAuth can block embedded webviews, GitHub SAML state is tied to an authenticated browser session, and native view geometry may make splitter interactions fragile. Keep every stated requirement. Make P0 a short decision spike for auth, view composition, and Local ACP, then choose one Local interaction surface and the smallest tab model that passes user scenarios. Do not proceed to feature phases on “same web app” or “native views work” alone; verify those assumptions in the real tenant and on a packaged Windows build.

## Findings

1. **[major] Hosting Devin’s Cloud UI is the right first move; a native Cloud sidebar is not the simpler alternative on the evidence given.** The brief says folders have no documented public API and the v3 messages API omits worklog/approval/PR interactions, so a native session list and conversation would reproduce server behavior and still miss parity. A simpler compliant alternative is the plan’s web-first composition, but keep Cloud as one hosted surface and use native controls only for the app rail and GitHub pane; avoid a hybrid native session sidebar that shadows web state. Revisit native controls only when supported folder/worklog APIs exist, not by automating private endpoints. [Institutional brief §§1–2](./institutional-context-brief.md); [Devin ACP/Desktop docs](https://docs.devin.ai/desktop/devin).

2. **[major] P4 appears to build two Local clients; choose one complete Local interaction path.** P4a adds an embedded terminal for Devin CLI, then P4b adds an ACP chat UI. That duplicates input, history, and permissions surfaces unless the terminal is explicitly a fallback. Simpler alternative: make ACP chat the primary Local surface if the real CLI contract supports required session operations; retain terminal mode only as a deliberate troubleshooting/fallback path. If ACP history/resume is unavailable, a terminal-first Local mode can still be considered, but it must itself meet the agreed Local create/continue/interact expectations—do not quietly treat “a terminal launches” as complete Local support. Verify the installed `devin acp` capabilities; official docs show the CLI invocation and the requirement that `devin` be installed on `PATH`, but do not publish its negotiated session capabilities. [Devin ACP docs](https://docs.devin.ai/desktop/acp); [ACP v1 list capability](https://agentclientprotocol.com/protocol/v1/session-list); [ACP v2 migration](https://agentclientprotocol.com/protocol/v2/migration).

3. **[blocker] Embedded auth is a product gate, not an implementation detail.** Google’s OAuth policy blocks embedded webviews for OAuth authorization. If the Devin tenant or GitHub SAML identity flow redirects through Google, sign-in inside the Electron `WebContentsView` may fail even though ordinary pages load. GitHub documents that SSO requires an active IdP session in the browser and requires periodic reauthentication; the app’s separate `persist:github` partition should not be assumed to share a user’s Chrome cookies. Test the actual Cloud IdP and an SSO-protected GitHub org in P0. If embedded login is rejected, define an approved system-browser/native OAuth handoff that preserves the in-app Devin and GitHub views; do not copy cookies between browser profiles. [Google embedded-webview OAuth policy](https://developers.googleblog.com/en/upcoming-security-changes-to-googles-oauth-20-authorization-endpoint-in-embedded-webviews/); [GitHub SSO behavior](https://docs.github.com/en/enterprise-cloud@latest/authentication/authenticating-with-single-sign-on/about-authentication-with-single-sign-on); [Electron session partitions](https://electronjs.org/docs/latest/api/session).

4. **[major] Electron is the best current default if identical desktop Chromium matters, but “only stable choice” is too strong.** Electron’s `BaseWindow` + `WebContentsView` fits a React shell with multiple Chromium surfaces, and it avoids Tauri’s documented unstable child-webview API and synchronous Windows deadlock caveat. For a Windows-only optimization, WinUI 3 + WebView2 is a credible native-shell alternative and Microsoft documents WebView2 in WinUI 3; however, the required multi-view tabs and later macOS support would still need a proof and a separate platform implementation. Tauri is another lower-download alternative, but its child-view caveats make it less attractive for this particular composition today. A short spike comparing shell startup, auth, multiple views, focus/resize behavior, and packaging is better evidence than treating any framework as categorically superior. [Electron BaseWindow](https://electronjs.org/docs/latest/api/base-window); [Tauri WebviewBuilder](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewBuilder.html); [Microsoft WinUI 3 WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/platforms/winui3-windows-app-sdk).

5. **[major] Native view z-order and splitter interaction are likely the hardest UI risk.** The plan says native views paint above `shellView`, so shell-owned tab chrome and controls must live outside their rectangles. The splitter is different: dragging starts in shell content and may cross into the Devin or GitHub view, where shell DOM pointer handling may no longer receive events. This can break the central docked-pane interaction even when static layout looks correct. Keep the P0 drag test, but test start/move/release across both native-view boundaries and at Windows scaling factors. Simpler compliant layout: make the splitter’s entire hit target shell-owned and use a main-process/native drag strategy if capture is lost; do not solve this by overlaying shell chrome over hosted content. [Electron child-view composition](https://electronjs.org/docs/latest/api/base-window); [Electron WebContentsView](https://electronjs.org/docs/latest/api/web-contents-view).

6. **[major] One live `WebContentsView` per tab can make “only active tab attached” an incomplete memory policy.** The plan retains a `WebContentsView` per tab and detaches inactive views; it does not say inactive `webContents` are suspended or destroyed. Measure memory and responsiveness on the Windows target at representative tab counts, including tabs that run long-lived pages. Simpler alternative: keep tab metadata for all tabs but lazily create views, and define an explicit inactive-view eviction threshold/reload policy if the benchmark requires one. Preserve open-tab URLs and titles so eviction does not remove the required tab behaviors. Electron warns that `BaseWindow` does not destroy child view `webContents` automatically on close, so close/cleanup needs explicit lifecycle tests. [Electron BaseWindow lifecycle](https://electronjs.org/docs/latest/api/base-window).

7. **[minor] Global tabs are simplest for the current single right pane, but need a clear session-context rule.** The plan’s global tab model avoids maintaining different tab collections for every Devin conversation. Alternative: associate each tab with its originating session and visibly retain that context while keeping one global strip; switch to per-session tab sets only if user research shows sessions need isolated workspaces. This preserves required titles/close/reorder while avoiding two tab-management systems. Decide whether clicking a different session keeps, filters, or restores the same global tabs, and test that GitHub auth/session state is not accidentally represented as Devin-session state.

8. **[minor] Trim the custom browser surface to the user’s stated tab needs.** The requirement is an in-app hosted Chromium pane with titles, close, and reorder; the plan adds back/forward/reload, copy URL, open externally, download handling, tab dedupe, shortcut routing, and reopen-closed-tab. These are useful but grow a browser-like subsystem the user explicitly does not want to build. Simpler alternative: ship the required `WebContentsView` host and minimum tab-strip behavior first, then add only navigation affordances shown necessary by the GitHub workflow. Keep the Chromium engine and content handling delegated to Electron; avoid an address bar, history/bookmark system, download manager, or browser settings surface.

9. **[minor] The mobile plan reuses code, but not the desktop product surface.** An Expo shell and GitHub tab sheet are a new UI implementation, and the plan states Devin Local is desktop-only. That may still be a reasonable later platform path, but “few changes” is not yet demonstrated. Alternative: keep the shared core platform-neutral and defer a mobile feasibility claim until a small proof shows the same Cloud/Local requirements and GitHub-pane behaviors can be represented on mobile. Do not present the omission of Local or the right-side pane as a mobile strategy unless the product owner explicitly changes those requirements.

## Challenge-mode conclusions

- **Embedding vs. native controls:** Keep the real Devin web UI for Cloud in the first release; native controls cannot currently prove folder and conversation parity from the documented API surface in the brief. The current web-first plan is simpler than duplicating that surface.
- **ACP vs. terminal:** Both are not automatically needed. Select one complete Local experience after a real `devin acp` contract check; keep terminal as a deliberate fallback only if necessary to preserve Local coverage.
- **Global vs. per-session tabs:** Start global with source/session context; per-session collections add state and persistence complexity without a requirement.
- **Electron vs. WebView2/Tauri:** Electron is the strongest default for a single React/Chromium desktop implementation. A Windows-native WebView2 route is credible only if its required composition works and the cost of the Mac adapter is accepted; Tauri requires an explicit solution to the documented multi-view constraints.
- **Risks that must be decided in P0:** real Google/Okta sign-in, GitHub SAML within the app’s partition, embedded Devin web-app behavior, splitter pointer capture/z-order, and multi-tab memory/lifecycle.
