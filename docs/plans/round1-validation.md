# Devin Workspaces — Round 1 plan review

## Verdict: APPROVE WITH CHANGES

The plan has a credible central choice: host the actual Devin web application for Cloud, because the supplied brief says public v3 APIs lack folders and the messages API omits important worklog interactions. Electron is also a plausible fit for the Windows-first, multi-`WebContentsView` composition, and its relevant APIs exist in the current official documentation. However, several “by construction” claims are not yet demonstrated, and the phase plan lacks requirement-level exit criteria. In particular, P1 does not prove folder parity, two-way sync, create-session, full session interactions, or live status against a real tenant; P4 does not settle which ACP version/capabilities the installed `devin acp` actually supports; and the mobile path is an architecture sketch rather than evidence that R10 can be met with few changes. Keep all R1–R12 intact, but make the stated behavior observable through explicit acceptance checks, including real-tenant and packaged-Windows evidence. Treat SSO and embedded-web behavior as go/no-go risks with a fallback plan, not as consequences of choosing Chromium.

## Findings

1. **[major] R1 — Folder parity is plausible, but not proved by the current checklist.** Hosting the real Devin app avoids reimplementing folder state through the incomplete public API described in the institutional brief. But the manual test says only “folder move”; it does not enumerate create, rename, move between folders, unfile, archive/delete behavior, persistence after reload, or visibility in both directions. Define the supported folder actions and verify each in the embedded app and a separate web browser/account session. The release note cited by the brief says folders are personal; the plan should verify behavior for the actual signed-in user, not infer parity from server ownership alone. [Brief §1](./institutional-context-brief.md); [Devin release notes](https://docs.devin.ai/release-notes/overview#june-12-2026).

2. **[major] R2 — “Interact exactly like the web UI” needs a workflow acceptance matrix.** The plan correctly notes that v3 `messages` omits worklog panels and other interactions, which supports embedding the real app. But the fixture E2E tests only link routing and GitHub tabs; the manual checklist does not explicitly exercise session selection and the consequential interaction surfaces (tool/worklog views, approvals, prompts, PR cards, and normal message send/stream). List the web behaviors in scope and run a real-tenant smoke through them inside Electron, including reload/reconnect. Do not treat matching the hosted page’s pixels or successful page load as proof of interaction parity. [Brief §1](./institutional-context-brief.md); [Plan §§2, 6](./round1-plan.md).

3. **[major] R3 — Session creation is deferred to P5 without a creation acceptance test.** P1 claims R1–R5, but P5 later adds `Ctrl+N` as navigation to a new-session page. Neither the E2E fixture nor the manual checklist asserts that a session can be created, appears in the Cloud UI, and can be selected and interacted with. Decide whether web-native creation is delivered in P1 or P5, then assert the created session is visible in the embedded app and web UI. If `Ctrl+N` is part of the deliverable, test it while focus is in each embedded view as well as in shell chrome.

4. **[major] R4 — Two-way sync is an assumption, not a demonstrated acceptance result.** The checklist mentions moving a folder in both directions, which is a good start, but does not define the mutation set, convergence condition, or a second client/browser used to observe changes. “Server-side state” does not prove the hosted page remains authenticated and operates normally inside this Electron session. Specify mutations and observable outcomes (including reload/reopen) for both directions; test with the same user in a separate web browser and record the result. Do not substitute the plan’s optional API polling for web UI sync.

5. **[major] R5 — “Live status” has no measurable meaning or coverage.** The checklist asks for “a live status change” but does not name states, source, update latency, or whether updates must continue while another pane has focus. The API polling in P5 is for notifications and is optional; it does not prove the hosted Cloud status UI updates. Define representative transitions (including waiting/approval and terminal states), a maximum observation delay, and a manual real-tenant test or deterministic fixture that asserts the visible status updates without reload.

6. **[major] R6 — The Local implementation mixes ACP versions and leaves the real CLI contract unverified.** The official TypeScript package is `@agentclientprotocol/sdk`; its README says v1 is the stable entry point and v2 is an explicit experimental import. In ACP v1, clients must check `sessionCapabilities.list` before `session/list`, and `session/load` is a separate optional capability. ACP v2 instead requires `session/list` for agents advertising the session surface and removes `session/load` in favor of `session/resume` with replay. The plan lists `session/list` and `session/load` without choosing a protocol version or defining negotiation/fallback. [ACP TypeScript SDK](https://www.npmjs.com/package/@agentclientprotocol/sdk); [ACP v1 session/list](https://agentclientprotocol.com/protocol/v1/session-list); [ACP v2 migration](https://agentclientprotocol.com/protocol/v2/migration).

   Devin’s official ACP docs show a local registry launching the CLI as `devin acp`, and explicitly assume the CLI is already installed and on `PATH`. They do **not** document which session-list/load/resume capabilities that binary advertises. The plan’s “if advertised” qualification is appropriate, but no evidence currently shows the required history capability is advertised by Devin’s CLI. Make the real contract check a P4 exit gate: capture `initialize`, branch according to the reported protocol/capabilities, create/prompt/cancel/reconnect a session, and state how the app behaves if history is unsupported. Also specify CLI discovery/install guidance and test the process lifecycle in the packaged Windows app. [Devin ACP docs](https://docs.devin.ai/desktop/acp); [Devin custom ACP agent docs](https://docs.devin.ai/desktop/acp-custom).

7. **[major] R7 — Routing coverage is narrower than “any github.com link.”** The unit tests list URL classes and the fixture covers `_blank`, an iframe link, and `window.open`, but acceptance should cover in-place/top-level navigation, redirects, link activation from Cloud, Local, and GitHub, and downloads/auth redirects. The `*.githubusercontent.com` download exception is a reasonable product behavior but should be stated as an exception to “opens in the pane” and tested; verify that no GitHub navigation falls through to the system browser. Electron documents `setWindowOpenHandler`, `will-navigate`, and `will-frame-navigate`; the existence of these hooks does not establish that all relevant sources, frames, redirects, and dispositions are wired correctly in this app. [Electron `webContents`](https://electronjs.org/docs/latest/api/web-contents).

8. **[minor] R8 — The plan reuses Electron’s hosted-view primitive, but should bound the custom browser surface.** `WebContentsView` is Electron’s documented component for hosting web contents inside a `BaseWindow`, so this is not building a rendering engine. The plan nevertheless owns tab lifecycle, navigation, history controls, URL copying, downloads, persistence, and keyboard behavior. Confirm “reuse” means using `WebContentsView` (and any available existing tab-host component), then keep non-required browser chrome out of scope unless it directly supports R9. Electron explicitly requires closing each view’s `webContents` when the `BaseWindow` closes to avoid leaks; the plan notes this for closed tabs but should also make window shutdown part of acceptance. [Electron `WebContentsView`](https://electronjs.org/docs/latest/api/web-contents-view); [Electron `BaseWindow`](https://electronjs.org/docs/latest/api/base-window).

9. **[minor] R9 — The most testable requirement is covered at the model level, but layout acceptance is missing.** Tab reducer tests and fixture assertions cover title, close, reorder, and some routing. Add a Windows packaged/manual check that the pane is actually docked to the conversation’s right, splitter resizing and collapse/restore work, title updates after navigation, and tab focus/keyboard controls do not steal or break page input. Native view bounds and shell chrome are separate surfaces, so the unit reducer cannot prove the visual arrangement or pointer behavior. Electron documents `BaseWindow` child views and their bounds, not this app’s splitter implementation. [Electron `WebContentsView`](https://electronjs.org/docs/latest/api/web-contents-view).

10. **[major] R10 — Windows packaging is testable; “mobile with few changes” is not established.** A `windows-latest` NSIS install/launch smoke is useful, but “smoke E2E” needs defined assertions and should run against the installed artifact, not only the development binary. Include upgrade/reinstall and persisted partition/settings checks. For the later mobile path, the plan proposes a new Expo/React Native shell and a GitHub tab sheet; reusing pure TypeScript models is useful but does not demonstrate “few changes,” and Devin Local is explicitly desktop-only in the proposal. Keep future support in scope as stated, and define which product capabilities must carry over plus a small cross-platform proof before claiming the path is low-change.

11. **[major] R11 — The framework comparison supports a hypothesis, not the “only stable” conclusion.** Electron’s APIs are documented, but the plan’s assertion that it is the *only* stable, documented, cross-platform-identical primitive is not demonstrated by the comparison; the same table lists WinUI 3/WebView2 as good on Windows, while the brief identifies Tauri’s `add_child` as unstable and its Windows caveat. The Electron choice is reasonable for Chromium consistency across desktop platforms, but cite current vendor docs and compare the exact required view composition, auth, updates, and mobile reuse. Playwright’s Electron support is officially described as experimental; explicit `WebContentsView` discovery was added in merged PR #39912, which tests `_electron.launch()` plus `electronApp.windows()`. Pin a Playwright release containing that support rather than assuming every version can inspect these views. [Playwright Electron API](https://playwright.dev/docs/api/class-electron); [Playwright PR #39912](https://github.com/microsoft/playwright/pull/39912); [Plan §3 / Brief §6](./round1-plan.md).

12. **[minor] R12 — The conditional “if feasible” decision is sound but should be scoped to documented interfaces.** The brief supports the conclusion that a native Cloud sidebar/conversation built only from documented v3 endpoints cannot currently reproduce folders and the full worklog. That does not prove local controls are impossible under every integration mechanism. State the decision more narrowly: native Cloud controls are not feasible using the documented/public API surface identified in the brief, so the Cloud surface remains the hosted app unless a supported folders/worklog API appears. This preserves the user’s conditional requirement without turning an API limitation into an absolute claim. [Brief §1](./institutional-context-brief.md).

13. **[major] Phase exits do not yet make the R1–R12 claims auditable.** P0 has useful spike checks, but no explicit result/evidence format or contingency if SSO fails. P1–P7 have deliverables but no objective exit criteria. At minimum:
   - **P0:** exact Electron/Playwright/ACP versions; real Devin tenant SSO; GitHub SAML in the isolated partition; all targeted `window.open`/navigation routes; drag across splitter while pointer crosses view bounds; keyboard capture. Record pass/fail and an SSO fallback decision.
   - **P1:** map R1–R5 to an action/status matrix, with real-tenant manual evidence for unsupported real-service behavior and fixtures for deterministic state transitions.
   - **P2:** verify R7–R9 end-to-end across every source and disposition, plus resize/focus/reorder and persistence/close cleanup.
   - **P3:** installed-artifact smoke with explicit launch, view creation, data persistence, update/upgrade, and uninstall expectations. “Code signing optional” and auto-update need an explicit release decision.
   - **P4:** real `devin acp` capability/version contract and a Windows packaged test, not just a fake-agent test; define both terminal and ACP-chat completion criteria.
   - **P5:** test PAT encryption on Windows and token never reaching renderer/logs; verify status notification conditions if these extras are retained.
   - **P6/P7:** specify macOS auth/signing and mobile capability gates before those phases are treated as support rather than evaluation.

## Factual checks performed

- **Electron APIs:** Official docs include `BaseWindow`, `WebContentsView`, `webContents.setWindowOpenHandler`, `will-navigate`, `will-frame-navigate`, and `before-input-event`. `before-input-event` is emitted before page key events, and the handler can prevent those events; this supports the proposed shortcut approach but still needs integration tests. [BaseWindow](https://electronjs.org/docs/latest/api/base-window), [WebContentsView](https://electronjs.org/docs/latest/api/web-contents-view), [webContents](https://electronjs.org/docs/latest/api/web-contents).
- **Lifecycle/security APIs:** `safeStorage` is documented; Electron recommends the async API. `app.enableSandbox()` exists and must be called before `ready`. The documented fuses include RunAsNode, cookie encryption, and embedded ASAR integrity validation; disabling RunAsNode has implications for `child_process.fork`, so validate packaged Local process behavior. [safeStorage](https://electronjs.org/docs/latest/api/safe-storage), [app](https://electronjs.org/docs/latest/api/app), [Electron fuses](https://electronjs.org/docs/latest/tutorial/fuses).
- **Playwright:** `_electron` exists but is documented as experimental. The WebContentsView-specific support is evidenced by the merged upstream PR’s added test for discovery via `electronApp.windows()`; pin a version that contains the change. [API](https://playwright.dev/docs/api/class-electron), [merged PR](https://github.com/microsoft/playwright/pull/39912).
- **ACP:** `@agentclientprotocol/sdk` is the correct official package name. v1 and v2 have different session-history contracts; the public Devin ACP docs establish `devin acp` invocation but do not establish which capabilities the real CLI advertises. [SDK](https://www.npmjs.com/package/@agentclientprotocol/sdk), [v1](https://agentclientprotocol.com/protocol/v1/session-list), [v2 migration](https://agentclientprotocol.com/protocol/v2/migration), [Devin ACP](https://docs.devin.ai/desktop/acp).
- **Embedded Google OAuth:** Google states embedded webviews are blocked for OAuth requests and advises native/external user-agent flows. If the actual Devin or GitHub SSO path redirects to Google, P0 can fail despite the Chromium view itself working; record the tenant’s actual IdP flow and an approved fallback. [Google Developers Blog](https://developers.googleblog.com/en/upcoming-security-changes-to-googles-oauth-20-authorization-endpoint-in-embedded-webviews/).
